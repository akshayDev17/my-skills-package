# Bootstrap a portfolio sub-app

Every sub-app of the site lives under its own path prefix (`/quiz`, `/graph`, …), in its own repo, deployed by that repo's CI. Before its first deploy it needs three things that used to be done by hand: a Cloudflare Access app guarding the prefix, its D1 database (and the id committed into `backend/wrangler.jsonc`, or the Worker config `--wrangler` names), and the repo's GitHub `production` environment with the deploy secrets. The bundled script does all three, idempotently, and prints the plan before changing anything.

The script is `scripts/portfolio-app.mjs`, next to this file. Run it with `node` (Node 20+); it is also the `portfolio-app` bin of the npm package `@akshaydev17/portfolio-app`.

## Inputs

- **Repo** — `owner/name` of the sub-app (e.g. `akshayDev17/graph-notes`).
- **Prefix** — the path it lives under (e.g. `/graph`). Refused: empty, `/`, and anything under ai-chat-archive's site-wide `/api`, `/_next` or `/vendors`.
- **Local clone** — a checkout of that repo; the D1 id is written into its `backend/wrangler.jsonc`.
- **Worker config** — optional `--wrangler <path>`, a path inside the clone, for a repo whose Worker config is not `backend/wrangler.jsonc` (chief-of-staff's is `shell/wrangler.jsonc`). It replaces the default for the whole run: the D1 plan and write, the messages that name the file, and, with `--public`, the R2 and Worker-name reads. A path that leaves the clone is refused. Pass it on the plan and on `--apply` alike.
- **D1 name** — optional; by default the `database_name` of the entry still holding a placeholder: `REPLACE_AFTER_d1_create` or `00000000-0000-0000-0000-000000000000`.
- **Public or private** — private (behind Access) unless the user explicitly says the app is public. Never choose public yourself, from the repo being public, the path, or anything else. Public adds `--public`.
- **Public paths of a private app (mixed)** — only the paths the user names, each as `--public-path <path>` (repeatable): `/<prefix>` itself, `/<prefix>/` (exactly the prefix's trailing-slash path; `/time-track` and `/time-track/` are different paths to Access; accepted only alongside `/<prefix>`, so pass both or the plan is a conflict), an exact path under it, or `<dir>/*`. Never add one the user did not name, never widen one (`/graph/api/public/*` must not become `/graph/api/*`), and never pass `--public` with them. Paths outside the prefix, `/<prefix>/*` and any other empty segment (`/<prefix>/x/`, `/<prefix>//`) are refused. A path without `/*` is meant to be public on its own: Cloudflare lets its children inherit its Bypass, so the script adds a narrowing `<path>/*` to the Allow app for each such path (none for `/<prefix>` or `/<prefix>/`, whose children the Allow app's `<prefix>/*` already covers), checks that a path under it still asks for sign-in, and stops if it does not. To make one more path public on an app that already has its public app, re-run with the full list plus the new path: the script adds only that destination to `<repo name> (public)`.

One-time machine setup (config file and the two keychain entries) is in the package README. If `bootstrap` reports a missing config or keychain entry, point the user there; never ask them to paste a token into the conversation.

## Steps

1. **Plan.**
   `node scripts/portfolio-app.mjs bootstrap --repo <owner/name> --path /<prefix> --clone <clone dir>`
   (add `--public` only for an app the user said is public, or one `--public-path` per public path the user named). This reads only. Each line is `✓` exists, `+` will be created, `-` will be deleted (only a public app's old Worker routes, replaced by `<prefix>*`), `!` a warning (for `--public`, that the path will be reachable by anyone), `·` information, `✗` conflict.
   *Done when the plan is printed and shown to the user verbatim.*

2. **Resolve conflicts (`✗`) by hand.** Exit code 2 means a conflict: an Access app that overlaps the prefix without matching it, an Access app or Access redirect on a path planned as `--public`, for `--public-path` an app other than `<repo name> (public)` already holding a listed path, a Bypass app opening more of the prefix than the list, an Allow app holding something unexpected or unable to take its narrowing destinations, a `<repo name> (public)` holding some of the listed paths but unable to take the rest, or `--public-path /<prefix>/` listed without `--public-path /<prefix>`, a Worker route that reaches into the prefix and is not the app's own, a clone of the wrong repo, an ambiguous `wrangler.jsonc`, a setup token missing a permission (the line names it; the user adds it in the Cloudflare dashboard), or a missing deploy-token keychain entry. The script will not apply while one stands. Report it; do not work around it, never remove an Access app to make `--public` pass, and never edit, remove or move a destination out of an existing app to make `--public-path` pass. The script's own `+ add narrowing destination(s) … to "<app>"` line is the one change it makes to an existing Allow app; it only shrinks what is public. Its `+ add public destination(s) … to Bypass app "<app>"` line is the one change it makes to an existing public app, and it adds only the paths the user named.
   *Done when a re-plan shows no `✗`.*

3. **Get explicit approval for the exact plan, then apply.** Creating a policy, an Access app or a public route changes who can reach the site, so `--apply` runs only after the user approves the printed plan in this conversation. Then re-run the same command with `--apply`. It creates the `+` lines in order. For a private app it first waits until the prefix redirects to `<team>.cloudflareaccess.com`, and stops with an error before touching anything else if it never does. For a mixed app it creates the Allow app with its narrowing destinations (or adds the missing ones to the existing Allow app), then the Bypass app (or adds the newly listed paths to the existing one), and waits until the private paths redirect and every listed public path answers signed out; the plan's "who answers" lines show which app covers each destination, the narrowing ones included. The private paths include `/<prefix>/portfolio-app-verify`, `/<prefix>/api/portfolio-app-verify` and a child of each public path listed without `/*`, and they now pass because of the narrowing destinations (for `/<prefix>/`, because of the Allow app's `<prefix>/*`, which the docs do not promise). If the error still names such a child (`<path>/portfolio-app-verify answered … not behind Access`), Cloudflare is letting the children of that exact path through despite the narrowing: both Access apps now exist and that path's children are public. Report it to the user at once and do not continue or change any Access app yourself; what to do next is their decision. **Only a run that adds `/<prefix>/` takes anything out again** (the plan's `<prefix>/<child>` line says whether this run does): if its wait fails, the script removes exactly `<domain>/<prefix>/` from the public app it added it to, keeps everything else that app holds (the bare `<domain>/<prefix>` always among it), deletes no app, then checks again without `/<prefix>/` and reports both; the run still exits 1. If a private path that asked for sign-in before `/<prefix>/` was added answers signed out, it does this at once rather than waiting. Report the error to the user verbatim: the first part says what failed, then `Rollback: removed <domain>/<prefix>/ from Bypass app "<name>", which keeps …` says what was removed, and the last part (`Without /<prefix>/ listed, …`) whether the site passes the check without it. The same removal runs if the write that adds `/<prefix>/` to the existing public app fails, since a write can go through and still fail. Do not re-run `--apply` or change any Access app yourself to get past it; what to do next is their decision. If the error says taking it out failed, `nothing was removed`, `it still holds it`, that the app now guards something other than expected, or (for a new public app) that the app `may exist all the same`, tell the user at once that paths under the prefix may still be public and that the app needs checking in the Zero Trust dashboard now. For a public app there is no Access wait; whenever `<domain>/<prefix>*` exists or the run creates it, it waits until `/<prefix>?portfolio-app-verify=1` answers as `/<prefix>` does (or redirects into the prefix) and `/<prefix>portfolio-app-verify` still comes from the origin (GitHub Pages), and only then deletes the Worker's old `<domain>/<prefix>` + `<domain>/<prefix>/*` (the `-` lines). If that check fails it deletes nothing, keeps `<domain>/<prefix>*` in place (the error says whether this run created it) and stops before GitHub; report the error verbatim. A re-run checks again, so it cannot end `done` while the check fails. An error naming `/<prefix>portfolio-app-verify` means the app's Worker does not pass outside paths to the origin (see below): the fix is in the app's repo, not a route change. If the plan said the Worker is not deployed yet, the route comes from a re-run after its first deploy.
   After the Access check passes, the run prints `AUD tag of Access app "<name>" (created|found): <tag>` for each Access app it created or found (the sign-in app, and the Bypass app of a mixed app); plan lines for apps that already exist end in `(AUD <tag>)`. The tag is the audience the app's Worker checks Access tokens against and is not a secret; give it to the user, who sets it in the app's Worker config. If a line says the tag was not in Cloudflare's answer, tell the user to read it from the app in the Zero Trust dashboard rather than guessing.
   *Done when the run ends with `done` (and, for a public app, a re-run after the first deploy shows the route `<domain>/<prefix>*` `✓` and no `-` line).*

4. **Commit the `wrangler.jsonc` change through the repo's normal delivery path.** The script edits the clone and never commits. The diff is one line: the placeholder replaced by the database id (in the file `--wrangler` named, if given).
   *Done when the change is on a branch headed for review.*

5. **Private apps only: gate the deploy on the login check.** Skip this for a public app; `verify` fails on a public path by design. The first step of the repo's deploy job should be:
   `npx -y @akshaydev17/portfolio-app@0.1.0 verify --domain akshayprabhakant.com --team shiny-moon-6b37 --path /<prefix>`
   (or `node <path>/portfolio-app.mjs verify …` until the package is on npm). It needs no secrets and exits non-zero unless both `/<prefix>` and a path under it redirect to Access. For a mixed app, add the same `--public-path` list (`/<prefix>/` included, if it is listed): then the private paths (`/<prefix>/api/…` and a child of each public path listed without `/*` among them) must redirect and each public path must answer signed out. A public path answering a bare 403 fails; that may be bot protection rather than Access, so check it in a private browser window.
   *Done when the deploy workflow runs `verify` before any deploy step.*

## The app's Worker route and its pass-through

A Cloudflare Worker route matches the whole URL, query string included, and a pattern cannot contain a query, so the exact route `<domain>/<prefix>` never matches `/<prefix>?<query>`: that request falls through to the zone's origin (GitHub Pages, a 404). The one pattern that matches it is `<domain>/<prefix>*`, which every app's Worker gets — from `--public` here, and in the app's own `frontend/wrangler.jsonc` (`"routes": [{ "pattern": "<domain>/<prefix>*", "zone_name": "<domain>" }]`) for the others. `<prefix>*` also matches siblings such as `/<prefix>foo` and `/<prefix>.html`, so the app's Worker must return `fetch(req)` untouched for every path that is neither `/<prefix>` nor under `/<prefix>/` (the README has the snippet). `bootstrap --public --apply` checks both for a public app. Access does not change with it: an Access app keeps exactly `<domain>/<prefix>` and `<domain>/<prefix>/*`, which already cover `/<prefix>?<query>`; `<prefix>*` there would put `/<prefix>foo` behind sign-in.

## Never

- Never run `--apply` without the user's approval of the plan it will carry out.
- Never print, log or echo a token. The script reads them from the keychain itself.
- Never give GitHub the setup token; only the narrow deploy token goes into `CLOUDFLARE_API_TOKEN`.
- Never widen an Access app beyond `<domain>/<prefix>` and `<domain>/<prefix>/*`, or a Worker route beyond `<domain>/<prefix>*`, whose Worker passes every path outside the prefix to the origin.
- Never pass `--public` unless the user explicitly asked for a public app.
- Never pass a `--public-path` the user did not name, or a wider one than they named.
